# BSE Natural Language Query Agent

Ask questions about a Brooklyn Sports & Entertainment ticketing database in natural language. The agent generates SQL, runs it read-only, and answers in business language.
The query it ran will always be returned as well, given a valid question.

```
? Show me the top 5 event categories by total revenue.

╭─ Answer ─────────────────────────────────────────────────────────────────────╮
│ NBA Regular Season is far and away the top revenue category at $345,780,832  │
│ across 510,519 tickets sold, nearly three times the next category.           │
│                                                                              │
│ Concerts rank second with $117,412,376 on 185,630 tickets, followed by NBA   │
│ Playoffs, WNBA and Comedy. These figures cover completed events and orders   │
│ only, and exclude comp tickets.                                              │
╰──────────────────────────────────────────────────────────────────────────────╯

Generated SQL
  SELECT c.name AS category, ROUND(SUM(t.price_paid + t.fees), 2) AS total_revenue, ...

Results (5 rows, 1.03s)
  category            total_revenue   tickets_sold
  NBA Regular Season  345,780,832.44       510,519
  Concert             117,412,376.46       185,630
  ...
```

## Getting started

Needs Python 3.12+.

```bash
uv sync
cp .env.example .env          # add your ANTHROPIC_API_KEY
uv run python data/seed.py    # builds data/bse.db, takes about 10s

uv run nlq                    # interactive
uv run nlq --demo             # the example questions from the brief
uv run nlq -q "Which concerts sold the most tickets last year?"
```

A lightweight Streamlit UI was also created. To run:

```bash
uv sync --extra ui
uv run streamlit run src/bse_nlq/app.py
```

Config all lives in `.env`, and every setting on `Settings` has an `NLQ_`-prefixed env
var. See `.env.example` for the full list with defaults. The ones you'd actually update
are `NLQ_MODEL`, `NLQ_MAX_ROWS`, `NLQ_FALLBACK_MODEL` and `NLQ_RESTRICTED_COLUMNS`.

Real env vars take precedence over the file, so `NLQ_MODEL=claude-haiku-4-5 uv run nlq` works for a
one-off. The `.env` lookup checks the cwd first and then the repo root, so running from
outside the project doesn't silently fail with something like "no API key".

`nlq -q` exits 0 on success and 1 on failure, and `--demo` exits non-zero if any
question errors, so both work as a smoke test.

## The data

The dataset is synthetic and is generated by `data/seed.py` from `data/schema.sql`. I went with generated
data instead of something off the shelf like Chinook so the three example questions in
the brief are answerable as a starting point.

The generator is seeded and anchored on today's date so time-relative questions keep
working whenever you run it. It contains about 80 events, 310k orders, 930k tickets and 4,000
customers over about 3.5 years. The exact counts move with the anchor date and the
seed srcipt prints them when it's done.

There are eight tables total and most queries will require a join.

```
venues ──────────┐                    event_categories
  venue_id       │                      category_id
  name           │                      name
  city, state    │                        │
  capacity       │                        │
                 ▼                        ▼
teams ───────► events ◄───────────────────┘
  team_id        event_id
  name           venue_id       → venues
  league         category_id    → event_categories
  is_bse_owned   home_team_id   → teams     (NULL for non-sporting events)
                 away_team_id   → teams
                 name, event_date, doors_time, announced_date, status
                   │
    customers      │
      customer_id  │
      name, email  ▼
      city, state, loyalty_tier
           └──► orders ──────────► tickets ◄───── seating_sections
                  order_id          ticket_id       section_id
                  customer_id       order_id        venue_id
                  event_id          event_id        name, level
                  order_ts          section_id      base_price
                  channel           seat_row/number
                  status            face_value, price_paid, fees
                                    is_comp, scanned_at
```

A few columns carry most of the business logic:

| Column | Importance |
|---|---|
| `orders.status` | only `completed` counts as a sale |
| `tickets.is_comp` | giveaways are `price_paid = 0` and would drag every average down |
| `tickets.price_paid` vs `face_value` | paid is revenue, face value is list price |
| `tickets.scanned_at` | NULL means no-show, so attendance isn't tickets sold |
| `events.home_team_id` | the right way to find Nets home games, not matching on the event name |

Dates are ISO-8601 text so SQLite's `date()` and `strftime()` and plain range
comparisons all work.

## How it works

There are two model calls per question:

```
  question
     │
     ▼
┌─────────────┐   key: question + business date + schema + prompt + model
│    cache    │ ──── hit ──► skip to audit ──► answer
└─────────────┘
     │ miss
     ▼
┌─────────────┐  structured outputs (JSON schema)      ┌──────────────────────┐
│    plan     │ ─────────────────────────────────────► │  ModelClient         │
│             │ ◄───────────────────────────────────── │  → claude-opus-5     │
└─────────────┘   SqlPlan{is_answerable, sql, ...}     │  (+ fallback model,  │
     │                                                 │   circuit breaker)   │
     │                                                 └──────────────────────┘
     ├── is_answerable = false ──► decline, explain what the DB does cover ──► done
     ▼
┌─────────────┐   sqlglot: one statement, SELECT only, inject LIMIT,
│    guard    │   + restricted columns when configured
└─────────────┘
     ▼
┌─────────────┐   read-only connection + SQLite authorizer + timeout
│   execute   │
└─────────────┘
     │
     ├── SQLite error ──► repair once (feed the error back) ──┐
     │                                                        │
     │  ◄─────────────────────────────────────────────────────┘
     ▼
┌─────────────┐   rows → markdown                     ┌──────────────────────┐
│ synthesize  │ ─────────────────────────────────────►│  ModelClient         │
│             │ ◄──────────────────────────────────── │  effort: low         │
└─────────────┘   plain-English answer                └──────────────────────┘
     │
     ▼
┌─────────────┐   one JSON record per question: id, outcome, latency, cost
│    audit    │ ◄── every path, cache hits included
└─────────────┘
     │
     ▼
  answer + SQL + results table + assumptions + request id
```

The planning call uses structured outputs, which is the more important part. It's set up that way so something like "I can't answer that" gets collapsed into `is_answerable: false` and I can have reliable handling instead of needing to pattern match free text. Synthesis is a second, cheaper call that
only sees the returned data, not the full schema. Doing it in one call would mean the answer gets
written without the actual results in front of it, which is how you get an answer
describing numbers that were never returned.

One wall clock deadline covers the whole proces. Every stage checks it before starting
and lowers its own timeout to whatever's left, so three retries across a plan call, a
repair and a synthesis call can't end up surpassing the total allotted time.

Each module was built to only do one thing. `agent.py` is orchestration only, `claude.py` owns the model
boundary, `guards.py` owns SQL validation, `prompts.py` holds all the prompt text, and
the operational stuff (`cache.py`, `deadline.py`, `observability.py`) lives in its own
files with its own tests rather than as branches inside `ask()`. `app.py` is 82 lines and
has no query logic in it. Both UIs call the same `NLQAgent.ask()`.

The agent depends on a `ModelClient` protocol, not on `anthropic` directly, so the tests
inject a fake and the whole pipeline including the repair loop runs in CI with no API key.

## Safety

SQL generated via LLMs against a real database gets a few guardrails:

1. The connection is opened read-only (`mode=ro`). This cannot be changed (for this current system) 
   and will hold even if other guardrails aren't working as expected.
2. A SQLite authorizer denies everything except SELECT, READ and FUNCTION, which blocks
   ATTACH and PRAGMA inside the engine.
3. `sqlglot` parses the SQL first: one statement only, root has to be a SELECT/WITH/UNION,
   and the whole AST gets walked so DML hidden in a CTE or behind a comment gets caught.
   This layer is more about good error messages than security.

Those checks are independent rule objects rather than an if-chain, which is what made
adding column-level access control a one-rule change. Set `NLQ_RESTRICTED_COLUMNS=email`
and the model is told about the restriction in the prompt so it declines cleanly and the
guard blocks it anyway if it tries. Turning that on also bans `SELECT *`, since otherwise
that's the way around it. `COUNT(*)` still works.

The sensitive column check is off by default since which columns are sensitive depends on the deployment,
and defaulting it on would ban `SELECT *` for everyone using a demo database.

On top of that there's a LIMIT injected into the AST (200 by default) and a wall clock
timeout enforced with `Connection.interrupt()` from a watchdog thread, so a hanging scan
aborts instead of stalling the UI.

Connections are per-thread. Streamlit serves every session from one cached `Database`,
and a single shared connection was both a correctness bug and a performance one.
`set_authorizer` is per-connection, so one thread's `finally` could clear the authorizer
while another thread was mid-query. Contention also turned 120 concurrent counts into
over 140 seconds. With `threading.local` connections the same workload runs in 0.14s with
the authorizer on for every thread.


## Prompt design

Most of the accuracy comes from here and it's all stored in `prompts.py`:

`schema_context.py` reads `PRAGMA table_info`
and `foreign_key_list` at startup so the prompt can't drift from the real schema.

The prompt lists every allowed literal for low-cardinality columns:

```
orders.status: 'cancelled', 'completed', 'refunded'
orders.channel: 'box_office', 'group_sales', 'mobile_app', 'resale', 'web'
```

Without this the most common failure would be `status = 'complete'`, which runs fine, returns zero
rows, and reports a confidently wrong answer. This block kills that whole class of bug.

A semantic layer, because column names don't imply business rules. Revenue is
`SUM(price_paid + fees)` on completed orders excluding comps. A Nets home game is
`home_team_id`, not a name match. Attendance is scanned tickets, not sold tickets. This
is what makes it answer like an analyst instead of like the columns literally read.

Four few-shot examples, including one worked example of declining, which teaches the
`is_answerable: false` path by showing it rather than describing it.

The whole thing is byte-stable for a given database and carries the cache breakpoint.
Today's date goes in the user turn, after the cached prefix, because putting it in the
system prompt would blow the cache on every request.

## Model choice

Defaults to `claude-opus-5`. SQL generation on multi-join analytical queries is the whole
task, and using a more capable model here might save a lot of headache over something like Sonnet or Haiku. A wrong query that runs is worse than a slow one. Native structured outputs and prompt caching matter here too, and with a 1M context I can inject the entire schema plus value hints and few-shots without
needing a retrieval layer.

Effort is set per step: `medium` for NL→SQL and `low` for synthesis, which is really just a
formatting task. `max_tokens` is 8000 on the translate step because thinking is on by
default on Opus 5 and `max_tokens` caps thinking and output together, so a tight budget
truncates.

Swapping is one env var. Haiku would probably be the best choice if cost is the primary concern.

## What would a real production pipeline look like

The pipeline waives auth, deployment and multi-turn, so this isn't a production service. There were a few things that were easy to implement beyond what was explicitly asked for in the assignment.

Every `ask()` gets a correlation id, stamped on the result
and shown in both UIs, plus the model id and a hash of the exact prompt that produced the
answer. One JSON line per question goes to the `bse_nlq.audit` logger with outcome,
latency, tokens, repair and cache status. Set `NLQ_AUDIT_LOG_PATH` and the same record
gets appended to a JSONL file.

Result rows are deliberately not in there. The trail records that a query read
`customers`, not what it read back, so it doesn't become a second unguarded copy of the
data. A failed write warns once per process and never fails the question.

TTL + LRU cache keyed on the question, the business date,
the schema fingerprint, the prompt version and the model. Every part of that key earns
its place: without the business date "last month" could get served tomorrow from
yesterday's window, and without the fingerprint a migration would keep serving answers
from a schema that no longer exists. Failures never get cached. A hit reports zero usage,
otherwise a cost dashboard would bill every repeat for calls that never happened. Measured
on a repeat: 6.75s → 0.01s.

Streamlit caches one agent for the life of the
process, so a migration would otherwise leave the prompt describing columns that are gone.
The agent re-checks a cheap PRAGMA-only fingerprint on an interval and rebuilds when it
changes.

Set `NLQ_FALLBACK_MODEL` and it falls through on
a rate limit, a 5xx or a connection failure. A model that keeps failing gets tripped out
of rotation for a cooldown so every later question skips it instead of paying the full
retry budget against something already known to be down. Permanent errors like a bad key
don't fall through, since they'd fail the same way everywhere.

## Testing

205 tests run with no API key (`uv run pytest -m "not llm"`). They cover the guards, the
read-only enforcement, the full pipeline against the real database with a fake model
client (happy path, declining, empty results, unsafe SQL, repair success, repair give-up,
malformed output), retry policy, config parsing, the cache, the deadline, the fallback and
breaker, concurrency, and the audit record.

The accuracy eval (`uv run pytest -m llm`) is 10 cases in `tests/eval_cases.yaml`, scored
on result equivalence against hand-written gold SQL rather than SQL string match. The
agent can order, alias or add columns however it wants as long as the answer agrees.
Grading on column position would reintroduce exactly the brittleness that result scoring
exists to avoid. Three of the cases check that it declines instead of inventing an answer.
Currently 10/10 passing, in about 70 seconds.

CI runs lint plus the no-key suite on every push, seeding with a fixed `--anchor-date` so
results don't drift with the calendar. A second job runs the eval against the real API on
main, weekly, and on demand, so a prompt or model change that regresses accuracy fails a
build instead of reaching a user.

## Tradeoffs

SQLite over DuckDB: SQLite is more akin to something I'd use in a production system (I tend to favor Postgres), but its date handling is much worse for something like this than DuckDB. No `date_trunc`, `INTERVAL`, or `EXTRACT` so "last month"
is `date('now','start of month','-1 month')`.

The 120-day backfill in the seed: Real NBA games don't happen in August, so "Nets home
games last month" would return zero rows in the off-season and the headline demo would
look broken. The seed backfills Nets home games across the trailing 120 days. 

I thought about giving the model a
`run_sql` tool and letting it iterate. One bounded retry fixes the common failure (wrong
column, wrong join key) while keeping latency predictable and the SQL auditable. The
transparency the brief asks for is easier when there's one final query instead of a trace
of twelve.


## What I'd do next

- Multi-turn, so follow-ups like "now break that down by month" work.
- A real semantic layer. Metric definitions live in the prompt right now and belong in a
  versioned YAML the agent and BI tools both read, so "revenue" can't drift between them.
- User identity, so column restrictions are per user instead of per deployment.
- Cost enforcement. Tokens are measured and audited but nothing is capped.
- A service boundary. A FastAPI layer over `NLQAgent` would let a Slack bot, the UI and
  the CLI share one deployment, cache, and audit log.
- A feedback loop where users flag a wrong answer and corrected pairs get promoted into
  the few-shot set
